# Paged Candidate List with a selectable roman fallback

The **Candidate List** can now hold up to twenty choices and is paged ten at a time; Space still cycles one candidate at a time and the page flips automatically when the selection crosses a page boundary, so a user can reach every candidate — including the raw roman **Commit Rules** floor — without any new navigation gesture. Digit keys select the candidate *on the visible page* (`1`–`9`, and `0` for the tenth row), and the raw roman fallback is now shown as the last candidate instead of being silently filtered out. Page size is a per-adapter knob (`ImeSessionOptions.page_size`, default 9); only IBus opts into 10 for now, so TSF and the macOS IMK keep their current behaviour until they opt in too.

We reached this design by walking the decision tree across nine branches. Most of the changes are individually small, but their *combination* is the contract: the page-relative digit math, the `page_size` gate, and the fallback flag only make sense together.

## The key decisions

- **Pagination state lives in the session, not the adapter.** `ImeSession` owns `page_size`; the "current page" is derived arithmetically from `selected_index` (`selected_index / page_size`), so there is no new page cursor to keep in sync. Every adapter that drives the shared `khmerime_session::ImeSession` gets identical selection behaviour for free, and the thin adapters (the IBus Python engine forwards raw keyvals verbatim) stay thin. The cost — a display concern (how many rows the host paints) leaking into the core — is paid once as a single builder option rather than re-implemented per adapter.

- **`page_size` defaults to 9 and only IBus opts into 10.** The selection logic is shared across all three desktop adapters, so a hardcoded page size would silently break the others: TSF paints nine rows (`MAX_ROWS = 9`, `.take(9)`) and the macOS IMK uses IMKit's *native* candidate window where our pages do not map at all. Defaulting to 9 keeps TSF and macOS behaving exactly as before; IBus sets `page_size = 10` when it builds the session and bumps its `IBus.LookupTable` to a page size of 10 to match.

- **Digit selection is page-relative and `0` is gated on page size.** `keyval_to_digit_index` now yields an in-page slot `0..=9` (with `0` mapping to the tenth row). `handle_digit` accepts the keypress only when `slot < page_size` **and** the resulting absolute index is in range; otherwise the digit falls through to being typed literally. This gate is what makes the feature safe cross-platform: on a 9-row adapter, slot 9 (the `0` key) fails `slot < page_size`, so `0` still types the literal character `0` during a **Composition**, exactly as today. Digits only ever select during an active **Composition** — with an empty buffer they are typed literally — so overloading `0` costs the user nothing they had before.

- **Space is unchanged — it cycles one candidate, not one page.** We deliberately did *not* repurpose Space into a page-jump key. Keeping `handle_space` as `cycle_candidates(1)` preserves the existing selection model (and the `space_cycles_candidates` test), keeps digit keys selecting the visible page, and lets pagination emerge from cursor movement: as the selection advances past index 9 the `IBus.LookupTable` flips to the next page on its own. The trade-off is that reaching the tail of a full two-page list takes more Space presses; we accepted this because the common case is a short list and jump-by-page would have broken the established Space semantics for a rarely-needed traversal.

- **The raw roman fallback is a first-class, selectable candidate — surfaced via an explicit flag.** The **Commit Rules** already keep the raw roman string as the final floor and the decoder already pins it as the last candidate, but the IBus renderer was dropping it: `ibus_candidate_renderer.candidate_rows` filters out any ASCII output (`if output.isascii(): continue`), and the roman literal is always ASCII. Rather than remove that filter wholesale — which would also let *intermediate* ASCII strings leak into the **Candidate List** — we add an `is_raw_fallback` flag to `CandidateDisplayEntry`, set in the snapshot when a candidate is the raw-literal floor, and admit an ASCII row *only* when that flag is set. The flag is self-documenting and portable, so TSF and macOS can honour the same signal when they adopt paging.

- **The candidate ceiling is 20, and it is a per-config knob — not the global constant.** The legacy roman-lookup suggester hard-caps at `MAX_SUGGESTIONS` (15), and the decoder config caps again at `max_candidates`; the effective visible ceiling was `min(15, 10) = 10`. Rather than bump the global `MAX_SUGGESTIONS`, we added a `max_suggestions` field to `DecoderConfig`: the interactive/visible config (`shadow_interactive`, which feeds the IBus **Candidate List**) uses 20, while the weighted-span/`default` config stays 15. The reason for the split is subtle but important: `LegacyData::suggest` applies its cap as an **early break during collection, before the priority sort**, so the cap size also decides *which* candidates enter the ranking. A global bump would therefore re-rank the weighted-span decoder's legacy pool — a commit-quality path guarded by a locked golden — not merely show more rows. Keeping the cap per-config means raising the visible count perturbs nothing downstream. We rejected a 30-item ceiling because candidate count is data-dependent — a given roman spelling has only as many Khmer entries as the **Lexicon** holds homophones for it, so most inputs stay well under one page and the extra headroom would be unused. Both caps are `truncate`/early-stop limits over an already-scanned match set, so raising them does not touch the hot-path latency budget (see [[0005-commit-refiner-keeps-a-latency-budget]] and the measured-fast engine finding).

## What this constrains

1. `ImeSessionOptions` gains a `page_size` field; the default must stay 9 so existing adapters are byte-for-byte unchanged until they opt in.
2. `keyval_to_digit_index` must return the in-page slot including `0`, and `handle_digit` must own the page-relative → absolute mapping and the `slot < page_size` gate. No adapter may pre-translate digits; the raw keyval flows to the session as before.
3. `CandidateDisplayEntry` gains `is_raw_fallback: bool`; the snapshot builder sets it, and any renderer that filters candidate rows (IBus today) must special-case it.
4. The IBus `IBus.LookupTable` page size and the session's `page_size` must stay equal (both 10). If they ever diverge, page-relative digit selection and the auto-flip page break.
5. `DecoderConfig` gains a `max_suggestions` field threaded through `LegacyDecoder` into `LegacyData::suggest_with_limit`; the visible/interactive config raises it to 20 while `default` (the weighted-span/commit-quality path) stays 15, so decoder ranking goldens are untouched.

## When to revisit

- **TSF or the macOS IMK adopt paging.** They set their own `page_size`, bump their row cap, and honour `is_raw_fallback`; the "default 9, IBus-only" scoping in this ADR is then superseded.
- **The dictionary or a model provider starts returning many more distinct candidates per spelling.** The shared ceiling of 20 (and the two-page assumption) would want re-tuning, and a jump-by-page key might finally earn its place.
- **Users demand direct page navigation** (Page Up/Down or clicking a page). The "pagination emerges from Space + cursor movement" decision would flip toward explicit page keys wired through the session.
