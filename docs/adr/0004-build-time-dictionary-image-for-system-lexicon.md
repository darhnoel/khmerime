# Adopt a build-time Dictionary Image for system Lexicon memory reduction

KhmerIME's Linux **Bridge** currently keeps the system **Lexicon** as heap-owned Rust maps, vectors, and strings inside **SharedTransliteratorData**, which measured around 168 MB RSS for synchronous full startup and over 200 MB in the current async Phase A/Phase B path. We will move the default system **Lexicon** toward a build-time **Dictionary Image**: a compact immutable binary image exposed through zero-copy views, first embedded with `include_bytes!` and designed so the same offset-based layout can be supplied by mmap later.

The first format should use sorted arrays, packed string tables, ID-keyed records, and range/posting tables rather than a LOUDS trie. This keeps the implementation tractable while removing the largest current sources of memory waste: duplicated string ownership, `HashMap` bucket overhead, and per-key `Vec` allocation. LOUDS remains a later option for prefix-heavy surfaces once the simpler image proves the boundary.

The first implementation slice will coexist with the current `LegacyData` path and validate exact plus alias lookup before routing production behavior through the image. Repeated strings must use numeric IDs from the start, with fixed-width records and `u32::MAX` reserved as the missing-string sentinel for optional fields such as boundary tags. The durable image format will be a manual little-endian layout with a magic header, schema version, section table, fixed-width records, and a packed UTF-8 string blob, rather than `rkyv` or bincode.

The builder and validator should live in core-owned code with `build.rs` acting as a thin orchestrator, and the runtime `DictionaryImageView` should remain internal behind `roman_lookup` rather than becoming public API. After coexistence validation, the first production routing target is weighted-span retrieval, because the largest measured heap structures are the ranked entry table, exact/alias indexes, ngram postings, and corpus stats used by that path.

We will preserve current IME behavior, leave **Learned History** on its existing TSV/HashMap path, and use Bridge steady-state RSS under 60 MB as the first serious milestone. We explicitly reject mmap of the current bincode cache as a solution: bincode still requires deserialization into heap-owned structures, so mmap only becomes useful after the storage format is changed to direct offset/range access.
